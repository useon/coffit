# Coffit AI Workflow

이 문서는 Coffit의 코드 변경을 수행하는 AI가 공통으로 따라야 하는 workflow다.
특정 도구의 Skill이나 UI 설정이 아니라 저장소의 portable source of truth로 관리한다.

## 적용 범위

새 기능, 버그 수정, 리팩터링, 기존 변경 리뷰, PR 준비 요청에 적용한다.
단순한 개념 질문이나 저장소 탐색만 필요한 요청에는 전체 workflow를 강제하지 않는다.

## 실행 모드

- **Build**: 새 기능, 버그 수정, 리팩터링을 구현한다.
- **Review**: 현재 diff가 Issue의 의도와 적용 가능한 Rules를 지키는지 검토한다.
- **Prepare**: 검증된 변경을 바탕으로 PR 본문 초안을 작성한다.

사용자가 모드를 명시하지 않으면 요청의 동사를 기준으로 선택하고, 애매하면 현재
변경 상태를 먼저 확인한 뒤 가장 작은 범위로 진행한다.

## 공통 시작 절차

1. `AGENTS.md`와 `CLAUDE.md`를 읽고 저장소 작업 규칙을 적용한다.
2. 작업을 연결할 Issue가 있는지 확인한다. Issue가 없으면 목표, 완료 조건,
   검증 방법을 먼저 정리해 Issue 초안을 만들고, 실제 Issue 생성은 사용자가
   명시적으로 요청한 경우에만 수행한다.
3. 현재 브랜치, base branch, `git status`, 기존 diff를 확인한다. 새 작업은 Issue
   번호와 작업 성격에 맞는 브랜치에서 시작한다.
4. 수정 대상 경로에 적용되는 `docs/ai/rules/`를 확인한다. Claude Code에서는 경로별
   `.claude/rules/` 어댑터가 같은 원본을 자동으로 연결한다.
5. 관련 Issue, 작업 노트, 유사 구현을 필요한 만큼만 읽는다.
6. 사용자가 만든 변경은 보존하고, 요청 범위 밖의 리팩터링은 하지 않는다.

### 컨텍스트 우선순위

작업 중 정보가 충돌하면 다음 순서로 판단한다.

1. `AGENTS.md`와 `CLAUDE.md`의 저장소 규칙
2. Issue와 사용자가 승인한 요구사항
3. `docs/ai/rules/`의 프로젝트 컨벤션
4. 기존 코드와 테스트가 보여주는 현재 동작
5. AI의 추정

AI의 추정은 사실처럼 적용하지 않고 가정으로 표시한다. 상위 정보가 충돌하거나
완료 조건을 판단할 수 없으면 구현을 진행하지 말고 확인이 필요한 내용을 보고한다.

### Issue 생성 요청

사용자가 Issue 생성을 요청하면 먼저 `.github/AI_ISSUE_GUIDE.md`와 해당 Issue
템플릿을 읽는다. Issue를 바로 생성하지 않고 다음 초안을 먼저 보여준다.

- `[PREFIX]` 형식의 제목
- 템플릿을 따른 본문
- 라벨, 마일스톤, assignee

Issue 제목, 본문, 작업 목록의 작성 형식은 `.github/AI_ISSUE_GUIDE.md`를 따른다.

Issue는 사용자가 초안을 승인한 뒤에만 생성한다. 생성 후에는 가이드에 따라 원격
`release`를 기준으로 `gh issue develop --base release`를 사용해 작업 브랜치를
만든다.

## Build 모드

1. 목표와 완료 조건을 한 문단으로 요약한다.
2. 변경 범위를 파일 또는 책임 단위로 제한한다.
3. 한 논리적 구현 단위만 수행한다. 서로 다른 목적의 변경을 한 번에 묶지 않는다.
4. 변경 범위에 맞는 검증을 실행한다.
5. 커밋하지 않고 handoff 형식으로 보고한 뒤 멈춘다.

검증 명령은 변경 범위에 맞춰 선택한다.

- 웹 변경: `pnpm lint`, 필요 시 `pnpm build:web`
- API 변경: `pnpm test:api`, 필요 시 `pnpm build:api`
- 문서·Rule만 변경: frontmatter, 경로, 링크, diff를 확인한다.

검증이 실패하면 원인을 먼저 분류하고, 요청 범위와 관련된 문제만 수정한다. 통과를
위해 테스트를 삭제·완화하거나 오류를 무시하지 않는다. 해결하지 못한 실패와 남은
위험은 handoff에 명시한다.

## Review 모드

1. 변경의 목적과 설계 의도를 Issue, diff, 작업 노트에서 추출한다.
2. 적용된 Rules를 기준으로 이번 변경 전용 평가 항목을 만든다.
3. 변경 파일과 필요한 주변 코드만 읽고, 범위 밖의 품질 문제를 확장하지 않는다.
4. 발견사항을 심각도와 파일 위치와 함께 보고한다.
5. 수정이 필요하면 사용자의 요청 범위 안에서만 반영하고 검증한다.

리뷰는 구현을 다시 작성하는 절차가 아니다. 근거 없는 취향 지적보다 API 계약,
책임 경계, 기존 사용자 흐름, 테스트 가능한 회귀 위험을 우선한다.

## Prepare 모드

PR 본문은 저장소 템플릿을 따르고 다음 내용을 포함한다.

- 관련 Issue
- 변경 배경과 작업 내용
- 설계 판단 또는 가정

PR 본문은 간결하게 쓰되, 협업 문서로 바로 사용할 수 있도록 존댓말로 작성한다.

외부 시스템에 PR을 생성하거나 메시지를 보내는 것은 사용자가 명시적으로 요청한
경우에만 수행한다. 요청이 없으면 본문 초안만 출력한다.

## Handoff 형식

```md
## 변경 단위

- 목표:
- 변경 파일:
- 적용한 Rule:
- 설계 판단:

## 검증

- 실행한 명령과 결과:
- 수동 확인:
- 미검증 항목 또는 남은 위험:

## 다음 단위

- 다음에 이어갈 최소 작업:
- 추천 커밋 메시지:
```

커밋은 사용자가 직접 수행한다.

## 하네스 변경 기준

실제 작업에서 같은 문제가 반복되거나, 프로젝트의 중요한 판단 기준으로 확인된
경우에만 Rule·Skill·workflow를 수정한다. 단 한 번의 불편이나 특정 작업의 예외를
일반 규칙으로 확장하지 않는다.
